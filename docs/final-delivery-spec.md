# 朋友圈最小闭环（V1）最终可交付版本说明

## 1. 文档目的
本说明定义本项目的最终交付边界、成功标准和模块验收口径，用于快速开发、面试讲解与结果验收对齐。

## 2. 项目目标（V1）
在仅使用伪代码与设计说明的前提下，完成以下最小闭环能力：
1. 好友系统：添加好友、查询好友列表
2. 发布动态
3. 查询某个人的动态列表
4. 从某个人视角查询其所有好友的动态时间线

## 3. 规模约束（强约束）
- 用户量级：10M+
- 单用户好友上限：5000
- 平均单用户动态数：100

这些约束必须直接体现在模型、访问路径和分页方案中，而不是仅停留在描述层面。

## 4. 架构基线（必须满足）
- 核心模型：`User + Friendship + Post + FeedInbox`
- 时间线模型：`fan-out on write`
- 查询分页：`cursor + limit`（优先基于 `createdAt + postId`）
- 禁止方案：
  - 读时动态聚合最多 5000 好友的全部动态再排序
  - 全表扫描
  - 深分页默认 `offset` 方案

## 5. 项目边界
### 5.1 本期必须做
- 数据模型/伪表结构
- 核心接口骨架
- 核心流程伪代码（好友、发动态、查个人动态、查好友时间线）
- 索引与分片的简要工程说明
- 复杂度与规模适配解释

### 5.2 本期明确不做
- 点赞、评论、图片/视频、推荐流、审核
- 真实框架代码、真实数据库代码、真实中间件代码
- 控制器层实现、部署与 CI/CD 细节
## 6. 最终成功标准（Definition of Success）
项目在以下条件全部满足时视为“成功交付”：
1. **范围正确**：只覆盖 4 个核心能力，无额外功能扩展。
2. **架构正确**：时间线读取路径基于 `FeedInbox`，非读时全量好友聚合。
3. **模型正确**：`Friendship` 为双向两条单向边；`Post` 与 `FeedInbox` 满足倒序查询模式。
4. **分页正确**：所有列表查询支持 `cursor + limit`，并说明为何优于深分页 offset。
5. **规模可解释**：能说明在 10M+/5000/100 约束下，为什么该方案可行、代价在哪里。
6. **表达可交付**：文档和伪代码足够面试讲解，不依赖具体框架细节。

## 7. 各模块达标线（验收口径）
### 7.1 User 模块
- 达标要求：
  - 具备最小身份字段（如 `userId`）与必要状态字段。
  - 支持按 `userId` 点查。
- 验收重点：
  - 主键访问路径明确、无扫描依赖。

### 7.2 Friendship 模块
- 达标要求：
  - 明确采用两条单向边表达好友关系（A->B, B->A）。
  - 支持按 `userId` 分页拉取好友列表。
- 验收重点：
  - 唯一约束/幂等语义清晰（如 `(userId, friendId)`）。
  - 访问路径是用户前缀索引读，而非图遍历。

### 7.3 Post 模块
- 达标要求：
  - 支持发布动态写入。
  - 支持按 `authorId + createdAt DESC` 查询个人动态。
- 验收重点：
  - 复合索引设计与游标分页匹配。
  - 能进行按 `postId` 批量回查详情。

### 7.4 FeedInbox 模块
- 达标要求：
  - 仅保存 `post` 引用与必要轻量信息（如 `postId/authorId/createdAt`）。
  - 支持按 `userId + createdAt DESC` 游标分页查询时间线。
- 验收重点：
  - 读路径为 `FeedInbox -> 批量回查 Post`。
  - 明确不保存完整正文，控制写扩散存储成本。

### 7.5 核心流程模块
- 达标要求：
  - `publishPost`：写 `Post` -> 查好友 -> fan-out 写 `FeedInbox`
  - `listUserPosts`：按作者倒序 + cursor 分页
  - `listFriendTimeline`：按 inbox 倒序 + 批量回查 post
- 验收重点：
  - 不出现读时遍历所有好友并归并排序的伪代码。
## 8. 为什么读时不能动态聚合 5000 好友
在“最多 5000 好友、平均每人 100 动态”前提下，单次时间线请求潜在候选集可到 50 万量级。若采用读时多路拉取并全量排序：
- 跨分区/跨索引读取量大，IO 与网络成本高
- 应用层排序和归并成本高，尾延迟不可控
- 并发放大后稳定性差，且深分页性能持续恶化

因此 V1 采用写扩散把复杂度前移到写路径，以换取读路径稳定和可预测性。

## 9. 索引与分片建议（简要）
- 索引：
  - `Friendship`: `UK(userId, friendId)` + `IDX(userId, createdAt DESC, friendId)`
  - `Post`: `PK(postId)` + `IDX(authorId, createdAt DESC, postId)`
  - `FeedInbox`: `PK(userId, createdAt DESC, postId)`（可选 `UK(userId, postId)`）
- 分片：
  - 优先按 `userId` 路由（`Friendship`/`FeedInbox`）
  - `Post` 按 `authorId` 或可路由主键策略

## 11. 高并发达标线（新增强约束）
为满足 10M+/5000/100 约束，以下条款必须在伪代码中明确：
1. Outbox 必须按分区消费，并定义每分区消费配额与积压阈值。
2. fan-out worker 必须支持热点 author 短窗口合并，避免重复读取 5000 好友。
3. 时间线读取必须包含 post_id 去重与缺失 post 降级策略。
4. 对账与恢复必须有明确 SLA（扫描周期、最大恢复时长、dead-letter 条件）。
5. FeedInbox 必须有硬性 retention 规则（时间窗口 + 每用户行数上限）。

## 12. 最终有条件通过修正项
本项目只有在以下修正项全部满足时，才视为当前题目的最终可交付版本：
1. publishMoment 重复 request_id 必须返回原 post_id。
2. fan-out worker 必须按最终 FeedInbox item 数切分批写。
3. FeedInbox 时间线只承诺 retention 窗口内的近期数据，历史归档不属于 V1。
4. fan-out 容量必须用 required_fanout_write_capacity >= publish_qps * avg_friend_count 表达。
5. 好友双边修复必须是持久化补偿任务，而不是仅同步兜底调用。

## 13. 发布入口准入达标线（P0新增）
publish 主链路必须包含入口级准入控制，形成“阈值 -> 行为 -> 返回语义”闭环：

- 阈值：
  - `soft threshold`（分区 pending 软阈值）
  - `hard threshold`（分区 pending 硬阈值）

- 行为：
  1. 低于 soft：正常接收
  2. soft/hard 之间：降级接收（可见性延迟）
  3. 超过 hard：受控拒绝（要求退避重试）

- 对外返回语义必须可判定：
  - `accepted`
  - `accepted_but_delayed`
  - `rejected_retry_later`

验收原则：
- 系统稳定性优先于“无限接单”；
- 高压下允许延迟可见与受控拒绝；
- 最终一致性目标保留（针对已接收请求）。
